# 동료평가 대비 질문답변

## 이 단계의 목표

평가자가 질문할 수 있는 운영/보안/자동화 질문에 스스로 답할 수 있게 준비한다.

## 왜 이 작업을 하는가?

평가 기준은 단순 실행 여부뿐 아니라 왜 그렇게 구성했는지 설명하는 능력을 포함한다.

## 사전 확인

README 요구사항 반영표와 실제 증빙을 먼저 완성한다.

## 예상 질문과 답변

### SSH 포트를 20022로 바꾼 이유는?

기본 22번 포트는 자동 스캔과 무차별 대입 공격의 흔한 대상이다. 20022로 변경하면 공격 시도를 줄일 수 있고, Root 접속 차단과 함께 기본 보안 수준을 높일 수 있다.

### Root 원격 접속을 차단한 이유는?

Root는 모든 권한을 가진 계정이라 탈취되면 피해가 크다. 일반 계정으로 로그인한 뒤 필요한 명령만 `sudo`로 실행하면 작업 기록과 권한 범위를 더 잘 관리할 수 있다.

### UFW에서 필요한 포트만 허용하는 이유는?

열려 있는 포트는 외부 공격면이 된다. SSH용 20022와 앱용 15034만 허용하면 서비스에 필요한 최소 통신만 유지할 수 있다.

### agent-common과 agent-core를 나눈 이유는?

`agent-common`은 세 계정이 공유 파일을 다루기 위한 그룹이고, `agent-core`는 운영자와 개발자만 민감 정보에 접근하기 위한 그룹이다.

### upload_files와 api_keys 권한을 다르게 둔 이유는?

업로드 파일은 테스트 계정도 접근해야 하지만, API 키는 민감 정보이므로 `agent-core`만 접근해야 한다. 이것이 최소 권한 원칙이다.

### monitor.sh에서 프로세스와 포트를 모두 확인하는 이유는?

프로세스가 살아 있어도 포트 바인딩에 실패하면 서비스는 응답하지 않는다. 반대로 포트만 보면 어떤 프로세스인지 놓칠 수 있으므로 둘 다 확인한다.

### 방화벽 비활성은 왜 exit 1이 아니라 WARNING인가?

앱 자체의 즉시 장애는 아니지만 운영 보안상 위험한 상태다. 그래서 관제 로그에는 남기되 프로세스/포트 장애처럼 즉시 실패로 종료하지 않는다.

### CPU/MEM/DISK 임계값 초과를 왜 WARNING으로 처리하는가?

임계값 초과는 성능 위험 신호지만 앱이 즉시 죽었다는 뜻은 아니다. 운영자는 경고를 보고 원인 분석과 증설, 정리 작업을 판단한다.

### `>`와 `>>`의 차이는?

`>`는 파일을 새로 쓰며 기존 내용을 덮어쓴다. `>>`는 기존 파일 뒤에 추가하므로 시간순 관제 로그에는 `>>`가 필요하다.

### logrotate가 필요한 이유는?

관제 로그는 계속 커진다. logrotate로 크기와 보존 개수를 제한하지 않으면 디스크가 가득 차서 더 큰 장애가 날 수 있다.
